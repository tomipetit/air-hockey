# スマホ対戦エアホッケー 仕様書（v0.1 ドラフト）

## 1. 概要

| 項目 | 内容 |
|---|---|
| ジャンル | 1対1 リアルタイム対戦エアホッケー |
| プレイ環境 | スマートフォン 2台（iOS Safari / Android Chrome） |
| 表示 | 3D。各プレイヤーは自分のゴール側から見下ろす視点 |
| 通信 | インターネット経由のリアルタイム通信（同じ部屋でも遠隔地でも可） |
| 配布形態 | Web アプリ（URL を開くだけで遊べる。インストール不要） |

### 1.1 前提とした判断（要確認）
- **ネイティブアプリではなく Web アプリ**とする。2台目のスマホにアプリを入れてもらう手間がなく、URL / QR コードで即参加できるため。将来 PWA 化でホーム画面追加にも対応可能。
- **縦持ち固定**。テーブルが縦長なので画面形状と合う。
- 1試合 **7点先取**（設定で変更可能にする）。

---

## 2. 技術スタック

| レイヤ | 採用技術 | 理由 |
|---|---|---|
| クライアント言語 | TypeScript | サーバーと物理演算コードを共有できる |
| 3D 描画 | Three.js | 実績・軽さ・スマホ対応 |
| ビルド | Vite | 開発体験が良く設定が少ない |
| サーバー | Node.js + `ws`（WebSocket） | シンプル、低遅延、NAT 越え不要 |
| 物理演算 | 自前実装（2D 円同士・円と壁の衝突） | エアホッケーは実質 2D 物理で十分。外部エンジン不要で決定的に動かせる |
| 共有コード | `shared/` パッケージ（物理・定数・メッセージ型） | サーバーとクライアントで同じロジックを使う |
| ホスティング | Fly.io / Render 等（WebSocket 対応 PaaS） | 低コストで常時稼働 |

### 2.1 通信方式の比較と選定

| 方式 | 長所 | 短所 |
|---|---|---|
| **WebSocket + 権威サーバー（採用）** | 実装が単純、不正・状態ズレが起きない、どのネットワークでも繋がる | サーバー経由のぶん遅延が +α |
| WebRTC DataChannel（P2P） | 同一 LAN なら最低遅延 | シグナリングサーバーと TURN が別途必要、実装が複雑 |

→ **まず WebSocket の権威サーバー方式で作り**、遅延が問題になれば後から WebRTC（unreliable/unordered チャネル）へ差し替えられるよう、通信層を抽象化しておく。

## 3. システム構成

```
 ┌──────────── スマホA ────────────┐        ┌──────── サーバー ────────┐        ┌──────────── スマホB ────────────┐
 │ タッチ入力 → マレット目標座標    │ input  │ ルーム管理               │ input  │ タッチ入力 → マレット目標座標    │
 │                                  │ ─────▶ │ 物理シミュレーション      │ ◀───── │                                  │
 │ 3D描画（Aのゴール側カメラ）      │ ◀───── │ 60Hz 固定ティック         │ ─────▶ │ 3D描画（Bのゴール側カメラ）      │
 │ 補間・自マレット即時反映         │ state  │ 得点判定・試合進行        │ state  │ 補間・自マレット即時反映         │
 └──────────────────────────────────┘        └──────────────────────────┘        └──────────────────────────────────┘
```

- **サーバーが唯一の正（権威）**：パック位置・得点はサーバーが決める。
- クライアントは「入力送信」と「受信状態の描画」に専念する。

## 4. ゲーム仕様

### 4.1 座標系とテーブル寸法（ワールド単位 = メートル相当）

上から見た 2D 平面 (x, z) で物理を計算し、描画時に y（高さ）を付与する。

```
          z = -1.0   ← P2 のゴール（P2 が守る）
     ┌──────[   ]──────┐
     │                  │
     │       P2 陣       │
     │                  │
x=-0.5 ─ ─ ─ ─ ─ ─ ─ ─ x=+0.5   ← センターライン z = 0
     │                  │
     │       P1 陣       │
     │                  │
     └──────[   ]──────┘
          z = +1.0   ← P1 のゴール（P1 が守る）
```

| パラメータ | 値（初期案） |
|---|---|
| テーブル幅 W | 1.0 |
| テーブル長 L | 2.0 |
| ゴール幅 | 0.30 |
| パック半径 | 0.040 |
| マレット半径 | 0.065 |
| パック最大速度 | 5.0 /s |
| マレット最大速度 | 6.0 /s |
| 壁の反発係数 | 0.90 |
| マレット–パック反発係数 | 0.95 |
| 摩擦（毎秒の速度減衰率） | 0.98 程度（エアテーブルなのでほぼ滑る） |

※ 値はプロトタイプで調整前提。すべて `shared/constants.ts` に集約する。

### 4.2 ルール
- パックが相手ゴールラインを完全に越えたら得点。
- 得点後、**失点した側の陣地**中央付近にパックを置いて再開（1秒の待機＋カウント表示）。
- 7点先取で勝利（設定可）。
- マレットは**自陣のみ**移動可能（センターラインを越えられない）。
- パックが一方の陣地で一定時間（例: 7秒）停止に近い状態なら、相手側からリスタート（膠着防止）。

### 4.3 物理演算
- 固定ティック **60Hz**、1ティック内を **4サブステップ**に分割（高速パックのすり抜け防止）。
- 衝突判定
  - パック ↔ 壁：軸ごとの反射。ゴール開口部は反射しない。ゴール角はコーナー円との衝突として扱う。
  - パック ↔ マレット：円–円衝突。マレットは無限質量扱い（相対速度で反射）、マレットの速度をパックに伝える。
- マレットの動き：クライアントからは「目標座標」が届く。サーバーは最大速度で制限しつつ目標へ移動させ、その移動量からマレット速度を算出する（瞬間移動で異常な速度が出るのを防ぐ）。

## 5. 3D 表示・視点

### 5.1 カメラ
- 両プレイヤーとも「自分のゴールが手前、相手が奥」に見える。
- 実装上は**ワールド座標は共通**、カメラ配置のみを変える。

| プレイヤー | カメラ位置 (x, y, z) | 注視点 |
|---|---|---|
| P1 | (0, 1.6, 1.9) | (0, 0, 0.1) |
| P2 | (0, 1.6, -1.9) | (0, 0, -0.1) |

- 画角（FOV）は端末のアスペクト比に応じて自動調整し、**テーブル全体が必ず画面に収まる**ようにする。
- 設定で「真上視点（2D風）」に切り替え可能にする（遠近感で操作しにくい人向け）。

### 5.2 描画要素
- テーブル（盤面・枠・センターライン・円・ゴール）
- パック、マレット×2（自分=青、相手=赤 など色分け）
- 影（パック・マレットの接地影。疑似影で軽量化）
- 得点表示（HUD は HTML オーバーレイ）
- エフェクト：衝突時の小さな火花、得点時のフラッシュ、端末振動（Vibration API、Android のみ）

### 5.3 パフォーマンス目標
- 描画 60fps（ミドルレンジ端末で）
- ポリゴン数は合計 2万 未満、テクスチャは最小限、リアルタイム影は使わない
- `devicePixelRatio` は最大 2 に制限

## 6. 操作

- 画面をタッチ・ドラッグすると、指の位置の**テーブル上の点**（レイキャストで求める）へマレットが追従。
- 指がマレットに隠れないよう、**マレットは指より少し奥（画面上方向）にオフセット**（設定で調整可）。
- 指を離してもマレットはその場に留まる。
- マルチタッチは最初の1本のみ採用。
- スクロール・ズーム・長押しメニュー等のブラウザ既定動作は無効化（`touch-action: none` など）。

## 7. 通信仕様

### 7.1 接続・マッチングの流れ

```
スマホA                      サーバー                      スマホB
  │  create_room ───────────▶ │                               │
  │ ◀─────── room_created(4桁コード, URL)                     │
  │  (画面にコードとQRを表示)  │                               │
  │                           │ ◀────────── join_room(コード)  │
  │ ◀──── player_joined ────  │ ───── joined(P2として) ─────▶ │
  │  ready ─────────────────▶ │ ◀───────────────── ready      │
  │ ◀──────── countdown(3,2,1) ───────────────────────────▶   │
  │ ◀════════ state（ゲーム中 毎秒30回）═════════════════▶    │
```

- ルームコード：4桁数字（例 `4821`）。招待用 URL `https://<host>/?room=4821` と QR コードも表示。
- ルームを作った側が P1、参加側が P2。
- 一定時間（10分）無通信のルームは破棄。

### 7.2 メッセージ定義（初期は JSON、最適化時にバイナリ化）

**クライアント → サーバー**

| type | 内容 | 頻度 |
|---|---|---|
| `create_room` | – | 1回 |
| `join_room` | `{ code }` | 1回 |
| `ready` | – | 試合開始前 |
| `input` | `{ seq, x, z }` マレット目標座標 | 最大60回/秒（変化時のみ） |
| `ping` | `{ t }` クライアント時刻 | 1回/秒 |
| `rematch` | – | 試合終了後 |

**サーバー → クライアント**

| type | 内容 |
|---|---|
| `room_created` | `{ code }` |
| `joined` | `{ side: 1 \| 2 }` |
| `player_joined` / `player_left` | 相手の入退室 |
| `countdown` | `{ n }` |
| `state` | `{ tick, puck:{x,z,vx,vz}, m1:{x,z}, m2:{x,z}, ackSeq }` |
| `goal` | `{ scorer, score:[p1,p2] }` |
| `game_over` | `{ winner, score }` |
| `pong` | `{ t, serverTime }` |
| `error` | `{ code, message }`（ルーム満員・存在しない等） |

### 7.3 同期・遅延対策
目標：**体感遅延 100ms 以内**、通信遅延 150ms 程度までは違和感なく遊べること。

1. **自分のマレットは即時描画**：入力をそのままローカルに反映し、サーバー応答を待たない。
2. **相手マレット・パックは補間描画**：受信したスナップショットを約 2 つ分（~66ms）遅らせてバッファし、線形補間で滑らかに表示。
3. **パックのローカル予測（フェーズ2）**：パックが自陣に来ている間は、共有物理コードでクライアント側でもパックを進め、自マレットとの衝突を即座に表示。サーバー状態が届いたら差分を数フレームかけて補正（リコンシリエーション）。
4. 時刻同期：`ping/pong` で RTT とサーバー時刻オフセットを推定。
5. スナップショット送信は 30Hz（帯域が許せば 60Hz）。1パケット約 60byte（バイナリ化時）。

### 7.4 切断時の扱い
- 相手が切断 → ゲーム一時停止、「相手の再接続を待っています」表示（最大 30 秒）。
- 再接続はルームコード＋セッショントークン（`joined` 時に発行し localStorage に保存）で同じ枠に復帰。
- 30 秒以内に戻らなければ残った側の勝利扱いでタイトルへ。

## 8. 画面遷移

```
[タイトル] ─┬─ 「部屋を作る」 → [待機画面: コード/QR表示] ──┐
            └─ 「部屋に入る」 → [コード入力] ───────────────┤
                                                            ▼
                                                 [カウントダウン]
                                                            ▼
                                                     [試合画面] ⇄ [一時停止(切断時)]
                                                            ▼
                                                    [結果画面] ─ 再戦 / タイトルへ
```

| 画面 | 主な要素 |
|---|---|
| タイトル | ロゴ、部屋を作る、部屋に入る、設定（視点・サウンド・振動・マレットオフセット） |
| 待機 | ルームコード（大きく）、QR コード、URL コピー、キャンセル |
| コード入力 | 4桁テンキー、参加ボタン、エラー表示 |
| 試合 | 3D テーブル、スコア、通信状態インジケーター（ping 値） |
| 結果 | 勝敗、スコア、再戦（両者が押したら開始）、タイトルへ |

- URL に `?room=XXXX` が付いていればコード入力を飛ばして直接参加。

## 9. サウンド
- パック–マレット衝突音、壁衝突音（速度に応じて音量変化）、得点音、カウントダウン音。
- Web Audio API 使用。iOS の制約のため、最初のタップでオーディオを有効化する。

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応ブラウザ | iOS Safari 16+、Android Chrome 最新2バージョン |
| 描画 | 60fps 目標、最低 30fps |
| 通信 | RTT 150ms までプレイ可能 |
| 同時ルーム数 | 初期は 1 サーバーで 100 ルーム程度 |
| セキュリティ | HTTPS / WSS 必須。入力値は範囲チェック（自陣外・NaN を拒否）。メッセージ頻度制限 |
| 画面 | 縦持ち固定。横向き時は「縦にしてください」表示。スリープ防止（Wake Lock API） |

## 13. 未決事項（ご確認ください）

1. **配布形態**：Web アプリ前提で問題ないか（App Store / Google Play 配信が必要か）。
2. **想定プレイ場所**：同じ部屋で遊ぶのが主か、遠隔地同士もあるか（同室専用なら WebRTC P2P の優先度が上がる）。
3. **見た目のテイスト**：リアル寄り（ゲームセンター筐体風）／ネオン・サイバー風／ポップ・かわいい系 など。
4. **追加要素の要否**：CPU 対戦（1人用）、ランダムマッチング、観戦、スキン、ランキング など。
5. **得点数・試合時間**：7点先取で良いか、時間制にするか。
