# スマホ対戦エアホッケー 仕様書（v0.2）

## 0. 確定事項

| 項目 | 決定 |
|---|---|
| 配布形態 | Web アプリ（URL / QR で参加、インストール不要） |
| プレイ場所 | **同じ部屋で 2 台を並べて遊ぶ**想定（同一 Wi-Fi が基本） |
| 見た目 | **ネオン風** |
| 勝敗 | **7 点先取** |
| CPU 対戦 | 後回し（M6）。ただし後付けできる設計にしておく |

## 1. 概要

| 項目 | 内容 |
|---|---|
| ジャンル | 1 対 1 リアルタイム対戦エアホッケー |
| プレイ環境 | スマートフォン 2 台（iOS Safari 16+ / Android Chrome） |
| 表示 | 3D。各プレイヤーは自分のゴール側から見下ろす視点 |
| 通信 | WebRTC による端末間の直接通信（P2P） |
| 画面向き | 縦持ち固定 |

## 2. 技術スタック

| レイヤ | 採用技術 | 理由 |
|---|---|---|
| 言語 | TypeScript | 物理・プロトコルを全体で共有 |
| 3D 描画 | Three.js（+ 後処理の Bloom） | ネオン発光表現に向く、スマホ実績あり |
| ビルド | Vite | 設定が少なく高速 |
| 端末間通信 | WebRTC DataChannel | 同室なら同一 LAN 内で直結でき、遅延が最小（数 ms〜20ms） |
| シグナリング | Node.js + `ws`（小さな WebSocket サーバー） | WebRTC の接続確立と、P2P 失敗時の中継にのみ使用 |
| 物理演算 | 自前実装（2D 円衝突） | 決定的で軽量。CPU 対戦にも流用 |
| ホスティング | 静的ファイル + シグナリングサーバーを Fly.io / Render 等に 1 つ | 低コスト |

### 2.1 通信方式の選定（v0.1 から変更）

同室プレイ前提のため、**WebRTC P2P ＋ ホスト権威方式**に変更する。

- 部屋を作った端末（P1）が**ホスト**として物理演算を実行し、状態の正を持つ。
- 参加した端末（P2）は入力を送り、ホストから届く状態を描画する。
- 同一 LAN の RTT は通常 5〜20ms なので、ホスト有利はほぼ体感できない。
- **フォールバック**：公衆 Wi-Fi のクライアント分離などで P2P が張れない場合は、シグナリングサーバーの WebSocket を経由して同じメッセージを中継する（通信層はインターフェースで抽象化し、上位コードは経路を意識しない）。
- 片方がモバイル回線でも、STUN（Google 公開 STUN）で多くの場合は直結可能。TURN は初期は用意しない。

## 3. システム構成

```
        ┌──────── シグナリングサーバー（接続確立時のみ）────────┐
        │  ルームコード管理 / SDP・ICE 中継 / P2P失敗時の中継   │
        └─────────────▲───────────────────────▲────────────────┘
                      │ WebSocket              │ WebSocket
 ┌─────── スマホA（P1 / ホスト）──────┐   ┌──────── スマホB（P2）────────┐
 │ タッチ入力                          │   │ タッチ入力                      │
 │ 物理シミュレーション（60Hz・正）    │◀══│ input                           │
 │ 得点判定・試合進行                  │══▶│ state（補間して描画）           │
 │ 3D描画（P1側カメラ）                │   │ 3D描画（P2側カメラ）            │
 └─────────────────────────────────────┘   └─────────────────────────────────┘
                     ◀══ WebRTC DataChannel（直結）══▶
```

- ゲームロジック（物理・試合進行）は `GameHost` クラスに閉じ込める。
  - オンライン対戦：P1 の端末内で `GameHost` を動かす
  - CPU 対戦（M6）：同じ `GameHost` を 1 台で動かし、P2 の入力を CPU AI が生成する

## 4. ゲーム仕様

### 4.1 座標系とテーブル寸法（ワールド単位 = メートル相当）

物理は上から見た 2D 平面 (x, z) で計算し、描画時に高さ y を付与する。

```
          z = -1.0   ← P2 のゴール（P2 が守る）
     ┌──────[   ]──────┐
     │       P2 陣       │
x=-0.5 ─ ─ ─ ─ ─ ─ ─ ─ x=+0.5   ← センターライン z = 0
     │       P1 陣       │
     └──────[   ]──────┘
          z = +1.0   ← P1 のゴール（P1 が守る）
```

| パラメータ | 値（初期案・要調整） |
|---|---|
| テーブル幅 / 長さ | 1.0 / 2.0 |
| ゴール幅 | 0.30 |
| パック半径 | 0.040 |
| マレット半径 | 0.065 |
| パック最大速度 | 5.0 /s |
| マレット最大速度 | 6.0 /s |
| 壁の反発係数 | 0.90 |
| マレット–パック反発係数 | 0.95 |
| 摩擦（毎秒の速度残存率） | 0.98 |

すべて `src/shared/constants.ts` に集約する。

### 4.2 ルール
- パックが相手ゴールラインを完全に越えたら得点。
- 得点後は**失点した側の陣地**にパックを置き、1 秒後に再開。
- **7 点先取**で勝利。
- マレットは**自陣内のみ**移動可能。
- パックが一方の陣地で 7 秒以上ほぼ停止していたら、相手側からリスタート（膠着防止）。

### 4.3 物理演算
- 固定ティック **60Hz**、1 ティックを **4 サブステップ**に分割（すり抜け防止）。
- パック ↔ 壁：軸ごとの反射。ゴール開口部は通過、ゴール角はコーナー円として衝突。
- パック ↔ マレット：円–円衝突。マレットは無限質量扱いで、マレット速度をパックに伝える。
- マレット：届いた「目標座標」へ最大速度を上限に移動し、その移動量から速度を算出（瞬間移動による異常速度を防止）。

## 5. 3D 表示・視点

### 5.1 カメラ
ワールド座標は共通で、カメラ配置だけを変える。どちらも「自分のゴールが手前」。

| プレイヤー | カメラ位置 (x, y, z) | 注視点 |
|---|---|---|
| P1 | (0, 1.6, 1.9) | (0, 0, 0.1) |
| P2 | (0, 1.6, -1.9) | (0, 0, -0.1) |

- 端末のアスペクト比から FOV を自動調整し、テーブル全体が必ず収まるようにする。
- 設定で「真上視点」に切替可能。

### 5.2 ネオン風アートディレクション

| 要素 | 表現 |
|---|---|
| 背景 | ほぼ黒（#05010f）、遠景にうっすら光るグリッド床 |
| 盤面 | 暗い半透明の黒〜濃紺。センターライン・センターサークル・ゴールエリアを発光ラインで描く |
| テーブル枠 | 発光チューブ（紫 #b026ff） |
| 自分のマレット | シアン #00f0ff の発光リング＋芯 |
| 相手のマレット | マゼンタ #ff2bd6 の発光リング＋芯 |
| パック | 白〜黄 #fff27a の強い発光。**速度に応じた残光トレイル** |
| ゴール | 守る側の色で発光。得点時に強くフラッシュ |
| HUD | ネオンサイン風フォント（例: Orbitron / Monoton）、スコアは発光文字 |
| エフェクト | 衝突時のパーティクル火花、壁ヒット時に枠の該当箇所が一瞬明るく、得点時の画面フラッシュ＋軽いカメラシェイク |
| 振動 | 衝突・得点時に Vibration API（Android のみ、iOS は非対応） |

**発光の実装方針（スマホ負荷対策）**
- 基本は `UnrealBloomPass` を**半解像度**で適用。
- 端末性能が低い場合（fps が 45 未満を数秒継続）は自動で Bloom を切り、加算合成のグロースプライト（偽グロー）に切り替える。
- 設定画面で「エフェクト：高 / 低」を手動選択可能。

### 5.3 パフォーマンス目標
- 描画 60fps（ミドルレンジ端末）、最低 30fps
- ポリゴン合計 2 万未満、リアルタイム影なし（接地影は円形の偽影）
- `devicePixelRatio` は最大 2 に制限

## 6. 操作

- タッチ・ドラッグした位置を、レイキャストで**テーブル上の点**に変換し、マレットが追従。
- マレットは指より少し画面上方向にオフセット（指で隠れないように。設定で調整可）。
- 指を離してもマレットはその場に留まる。マルチタッチは最初の 1 本のみ採用。
- スクロール・ズーム・長押しメニュー等は無効化（`touch-action: none`）。

## 7. 通信仕様

### 7.1 接続の流れ

```
スマホA(P1)              シグナリングサーバー              スマホB(P2)
  │ create_room ───────────▶ │                                 │
  │ ◀── room_created(4桁コード)                                 │
  │  (コード・QRを表示)       │ ◀──────────── join_room(コード) │
  │ ◀── peer_joined ──────── │ ──────── joined ──────────────▶ │
  │ ── offer(SDP) ─────────▶ │ ──────────────────────────────▶ │
  │ ◀─────────────────────── │ ◀────────────────── answer(SDP) │
  │ ⇄ ice_candidate ⇄ ⇄ ⇄ ⇄ ⇄│⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄ ⇄│
  │ ◀═══════════ DataChannel 確立（以降はサーバー不要）═══════▶ │
  │  ※5秒以内に確立できなければ WebSocket 中継モードへ          │
```

- ルームコード：4 桁数字。招待 URL `https://<host>/?room=4821` と QR を表示。
- 同室なので、P2 は**P1 の画面の QR をカメラで読む**のが主導線。
- 部屋を作った側が P1（ホスト）。

### 7.2 DataChannel 設定
- `ordered: false, maxRetransmits: 0`（遅れたパケットは捨てる。最新状態だけが重要）
- 試合進行イベント（得点・試合終了・再戦）は別チャネル `ordered: true`（信頼性あり）で送る。

### 7.3 メッセージ定義

**シグナリング（WebSocket）**

| type | 方向 | 内容 |
|---|---|---|
| `create_room` | C→S | – |
| `room_created` | S→C | `{ code }` |
| `join_room` | C→S | `{ code }` |
| `joined` / `peer_joined` / `peer_left` | S→C | 入退室通知 |
| `signal` | C⇄S⇄C | `{ sdp }` または `{ candidate }` を相手へ転送 |
| `relay` | C⇄S⇄C | P2P 失敗時のゲームメッセージ中継 |
| `error` | S→C | ルーム満員・存在しない等 |

**ゲーム（DataChannel、高頻度はバイナリ）**

| type | 方向 | 内容 | 頻度 |
|---|---|---|---|
| `input` | P2→P1 | `seq, x, z`（マレット目標座標） | 最大 60 回/秒 |
| `state` | P1→P2 | `tick, puck(x,z,vx,vz), m1(x,z), m2(x,z)` | 60 回/秒（約 40byte） |
| `event` | P1→P2 | `countdown / goal / game_over / pause` と点数 | 発生時 |
| `ready` / `rematch` | 双方向 | 準備完了・再戦希望 | 発生時 |
| `ping` / `pong` | 双方向 | RTT 計測 | 1 回/秒 |

### 7.4 同期・遅延対策
- **P1（ホスト）**：ローカルで物理を回すので遅延ゼロ。
- **P2**
  1. 自分のマレットは入力を即時描画（ホスト応答を待たない）。
  2. パック・相手マレットは受信状態を約 1 フレーム分（~16〜33ms）バッファして補間描画。
  3. 同室 LAN なら上記で十分な想定。中継モードや遅延が大きい場合のみ、パックのローカル予測（共有物理で先読みし、差分を数フレームかけて補正）を有効化（M5）。
- 画面右上に通信状態（ping 値と P2P / 中継の別）を表示。

### 7.5 切断時の扱い
- 相手が切断 → 一時停止し「再接続を待っています」表示（最大 30 秒）。
- 再接続はシグナリングサーバー経由で同じルームに復帰し、WebRTC を張り直す。
- **P1（ホスト）が切断された場合**：試合状態は P1 にしかないため、P1 が戻れば続行、30 秒で戻らなければ試合終了。
- 30 秒以内に戻らなければ残った側の勝利扱いで結果画面へ。

## 8. 画面遷移

```
[タイトル] ─┬─ 「部屋を作る」 → [待機: コード/QR表示] ──┐
            ├─ 「部屋に入る」 → [コード入力 / QR読取] ──┤
            └─ 「CPU と対戦」（M6） ─────────────┐     ▼
                                                 └─▶ [カウントダウン]
                                                            ▼
                                                     [試合] ⇄ [一時停止]
                                                            ▼
                                                    [結果] ─ 再戦 / タイトルへ
```

| 画面 | 主な要素 |
|---|---|
| タイトル | ネオンロゴ、部屋を作る、部屋に入る、設定（視点・エフェクト品質・サウンド・振動・マレットオフセット） |
| 待機 | ルームコード（大きく）、QR コード、キャンセル |
| コード入力 | 4 桁テンキー、参加ボタン |
| 試合 | 3D テーブル、スコア、通信状態 |
| 結果 | 勝敗、スコア、再戦（両者が押したら開始）、タイトルへ |

- URL に `?room=XXXX` があれば、コード入力を飛ばして直接参加。

## 9. サウンド
- シンセ系（ネオンに合わせたエレクトロ調）の効果音：マレットヒット、壁ヒット（速度で音量変化）、得点、カウントダウン。
- Web Audio API 使用。iOS の制約のため最初のタップでオーディオを有効化。
- BGM は M5 で検討（オン/オフ切替可）。

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応ブラウザ | iOS Safari 16+、Android Chrome 最新 2 バージョン |
| 描画 | 60fps 目標、最低 30fps |
| 通信 | 同一 LAN で入力から相手画面反映まで 50ms 以内 |
| セキュリティ | HTTPS / WSS 必須（WebRTC にも必要）。ホストは P2 の入力を範囲チェック（自陣外・NaN を拒否） |
| 画面 | 縦持ち固定、横向き時は案内表示。Wake Lock API でスリープ防止 |
| 開発時 | LAN 内のスマホ実機で試すため、Vite を HTTPS（自己署名証明書）で起動 |
