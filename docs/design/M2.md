# M2 詳細設計：2 台対戦の最小構成（＋ M3 の同期品質の最低限）

- 対象：SPEC v0.2 の M2「ルームコードで接続し、WebRTC で対戦・得点できる」と、M3 のうち
  「P2 の自マレット即時描画」「受信状態の補間」「中継フォールバック」。
- 前提：M1（`a85f5d9`）実装済み。本書だけで実装できる粒度で書く。迷ったら本書の「推奨」に従う。
- SPEC で確定している方針（ホスト権威 / WebRTC DataChannel / ws シグナリング / 5 秒で中継フォールバック /
  4 桁コード / 60Hz unreliable + reliable）は変更しない。

## 0. 全体像

```
 P1（ホスト）                               P2（ゲスト）
 ┌──────────────────────────┐             ┌──────────────────────────┐
 │ TouchInput(side=1)        │             │ TouchInput(side=2)        │
 │   ↓                       │   INPUT     │   ↓ 自マレットは即時描画   │
 │ NetHostDriver ─ GameHost ◀┼─────────────┼─ NetGuestDriver           │
 │   │ (物理・試合の正)       │   STATE/EVENT│   │ Interpolator(sync.ts) │
 │   └────────────▶ send ────┼────────────▶┼──▶│                       │
 │ TableView/CameraRig(1)    │             │ TableView/CameraRig(2)    │
 └────────────┬─────────────┘             └────────────┬─────────────┘
              │ NetSession ── Transport（WebRtcTransport | RelayTransport）│
              └──────────── SignalingClient（WebSocket /ws）────────────────┘
                                    │
                         server/main.ts（静的配信 + /ws）
                         server/signaling.ts + server/rooms.ts
```

- 上位コード（Driver）は `NetSession.send(msg)` / `onMessage` だけを使い、P2P か中継かを意識しない。
- main.ts の「CPU 固定」を `MatchDriver` インターフェースに置き換え、CPU / ホスト / ゲストの 3 実装を差し替える。

### 2.1 `src/shared/protocol.ts`

```ts
import type { Side } from './constants';

export const PROTO_VERSION = 1;
export const ROOM_CODE_RE = /^\d{4}$/;

// ---------- シグナリング（WebSocket テキストフレーム = JSON） ----------
export type SignalData =
  | { kind: 'offer'; sdp: string }
  | { kind: 'answer'; sdp: string }
  | { kind: 'candidate'; candidate: { candidate: string; sdpMid?: string | null; sdpMLineIndex?: number | null } }
  | { kind: 'relay' }; // ホスト → ゲスト：「中継モードに切り替える」

export type SignalErrorCode =
  | 'bad_request' | 'room_not_found' | 'room_full' | 'server_full' | 'version_mismatch' | 'already_in_room';

/** クライアント → サーバー */
export type ClientMsg =
  | { type: 'create_room'; v: number }
  | { type: 'join_room'; v: number; code: string; forceRelay?: boolean }
  | { type: 'signal'; data: SignalData }
  | { type: 'leave' };

/** サーバー → クライアント */
export type ServerMsg =
  | { type: 'room_created'; code: string }
  | { type: 'joined'; code: string }
  | { type: 'peer_joined'; forceRelay: boolean }
  | { type: 'peer_left' }
  | { type: 'signal'; data: SignalData }
  | { type: 'error'; code: SignalErrorCode };

/** JSON 文字列を検証して ClientMsg に。不正なら null（サーバーで使用） */
```

- SPEC 7.3 の `relay` メッセージは **WebSocket のバイナリフレーム**として実装する（JSON に包まない。ゲームパケットをそのまま転送し、エンコードを 1 種類に保つため）。テキストフレームは常にシグナリング JSON。

### 2.2 ゲームメッセージ（DataChannel / 中継共通、バイナリ、**リトルエンディアン**）

```ts
export const enum MsgType { State = 0x01, Input = 0x02, Event = 0x03, MatchStart = 0x04,
  Ready = 0x05, Rematch = 0x06, Bye = 0x07, Ping = 0x08, Pong = 0x09 }
```
（`isolatedModules: true` のため `const enum` は使わず、`as const` オブジェクト `MsgType = { State: 1, ... } as const` とする）

```ts
export type PhaseCode = 0 | 1 | 2 | 3; // countdown | playing | goal | over（GameHost の Phase と同順）

export interface StateMsg {
  type: 'state'; tick: number; phase: PhaseCode; puckActive: boolean; ackSeq: number;
  puck: { x: number; z: number; vx: number; vz: number };
  m1: { x: number; z: number }; m2: { x: number; z: number };
  score: [number, number];
}
export interface InputMsg { type: 'input'; seq: number; x: number; z: number }
export type WireEvent =
  | { kind: 'countdown'; n: number }
  | { kind: 'start' }
  | { kind: 'score'; scorer: Side; score: [number, number] }
  | { kind: 'stall'; serveTo: Side }
  | { kind: 'over'; winner: Side; score: [number, number] }
  | { kind: 'wall'; x: number; z: number; speed: number }
  | { kind: 'mallet'; side: Side; x: number; z: number; speed: number };
export interface EventMsg { type: 'event'; tick: number; ev: WireEvent }
export type GameMsg =
  | StateMsg | InputMsg | EventMsg
  | { type: 'match_start'; startTick: number }
  | { type: 'ready'; v: number }
  | { type: 'rematch' } | { type: 'bye' }
  | { type: 'ping'; t: number } | { type: 'pong'; t: number };

export type Channel = 'unreliable' | 'reliable';
export function channelOf(m: GameMsg): Channel; // state/input/ping/pong → unreliable、それ以外 → reliable
export function encode(m: GameMsg): Uint8Array;
/** 長さ不一致・未知 type・未知 kind・非有限の float を含む場合は null */
export function decode(buf: ArrayBuffer | Uint8Array): GameMsg | null;
/** u16 シーケンスの比較（ラップアラウンド対応）。a が b より新しければ true */
export function seqNewer(a: number, b: number): boolean; // d=(a-b)&0xffff; return d!==0 && d<0x8000
/** GameHost の GameEvent ⇄ WireEvent 変換（'goal' は送らないので null） */
export function toWireEvent(ev: GameEvent): WireEvent | null;
export function fromWireEvent(ev: WireEvent): GameEvent;
```

バイト配置（`DataView`、全て little-endian、アラインメント不要）。`f32`=Float32, `f64`=Float64。

**STATE 0x01（P1→P2, unreliable, 42 byte）**

| off | 型 | 内容 |
|---|---|---|
| 0 | u8 | type = 0x01 |
| 1 | u8 | flags: bit0 = puckActive, bit1-2 = phase(0..3), 他は 0 |
| 2 | u32 | tick（GameHost.tickCount） |
| 6 | u16 | ackSeq（ホストが最後に適用した P2 の input seq。未受信は 0。M2 では診断用、M5 予測で使用） |
| 8 | f32×4 | puck.x, puck.z, puck.vx, puck.vz |
| 24 | f32×4 | m1.x, m1.z, m2.x, m2.z |
| 40 | u8 | score[0] |
| 41 | u8 | score[1] |

**INPUT 0x02（P2→P1, unreliable, 11 byte）**：`0:u8 type` `1:u16 seq` `3:f32 x` `7:f32 z`

**EVENT 0x03（P1→P2, reliable）**：`0:u8 type` `1:u32 tick` `5:u8 kind` `6:payload`

| kind | 名前 | payload | 全長 |
|---|---|---|---|
| 1 | countdown | `u8 n` | 7 |
| 2 | start | なし | 6 |
| 3 | score | `u8 scorer, u8 s1, u8 s2` | 9 |
| 4 | stall | `u8 serveTo` | 7 |
| 5 | over | `u8 winner, u8 s1, u8 s2` | 9 |
| 6 | wall | `f32 x, f32 z, f32 speed` | 18 |
| 7 | mallet | `u8 side, f32 x, f32 z, f32 speed` | 19 |

**その他**

| type | 名前 | 方向 | ch | 配置 | 全長 |
|---|---|---|---|---|---|
| 0x04 | MATCH_START | P1→P2 | reliable | `0:u8, 1:u32 startTick` | 5 |
| 0x05 | READY | P2→P1 | reliable | `0:u8, 1:u8 v(PROTO_VERSION)` | 2 |
| 0x06 | REMATCH | 双方向 | reliable | `0:u8` | 1 |
| 0x07 | BYE | 双方向 | reliable | `0:u8` | 1 |
| 0x08 | PING | 双方向 | unreliable | `0:u8, 1:f64 t`（送信側 `performance.now()`） | 9 |
| 0x09 | PONG | 双方向 | unreliable | `0:u8, 1:f64 t`（PING の t をそのまま返す） | 9 |

decode の検証規則：全長が表と完全一致しない → null。`side`/`scorer`/`winner`/`serveTo` が 1,2 以外 → null。phase > 3 → null。float が `Number.isFinite` でない → null。

```ts
import type { Channel } from '../shared/protocol';
export type { Channel };
export type TransportKind = 'p2p' | 'relay';

export interface Transport {
  readonly kind: TransportKind;
  /** 両チャネルとも送信可能か */
  readonly isOpen: boolean;
  /** エンコード済みパケットを送る。閉じていれば黙って捨てる。
```

### 2.5 `src/net/webrtc.ts`

```ts
export interface WebRtcOptions { iceServers: RTCIceServer[]; blockIce: boolean }
export class WebRtcTransport implements Transport {
  readonly kind = 'p2p';
  constructor(role: 'host' | 'guest', sendSignal: (d: SignalData) => void, opts: WebRtcOptions);
  /** ホストのみ：offer を作って送る */
  start(): Promise<void>;
  /** 相手からの signal（offer/answer/candidate）を渡す */
  handleSignal(d: SignalData): Promise<void>;
  /** 両 DataChannel が open になったら呼ばれる */
  onOpen: (() => void) | null;
  // Transport のメンバー
}
```
内部仕様：
- `new RTCPeerConnection({ iceServers })`。既定 `iceServers = [{ urls: 'stun:stun.l.google.com:19302' }]`。
- DataChannel は **negotiated** で両側が同じ定義を作る（`ondatachannel` 不要・作成順の競合がない）：
  - `state`：`{ negotiated: true, id: 0, ordered: false, maxRetransmits: 0 }`
  - `event`：`{ negotiated: true, id: 1, ordered: true }`
  - 両方 `binaryType = 'arraybuffer'`。
- ホスト `start()`：`await pc.setLocalDescription(await pc.createOffer())` → `sendSignal({kind:'offer', sdp: pc.localDescription!.sdp})`。
- ゲスト offer 受信：`setRemoteDescription({type:'offer', sdp})` → キュー済み candidate を `addIceCandidate` → `setLocalDescription(await pc.createAnswer())` → answer 送信。
- ホスト answer 受信：`setRemoteDescription({type:'answer', sdp})` → キュー消化。
- `pc.onicecandidate`：`e.candidate` が null（収集終了）は送らない。それ以外は `{kind:'candidate', candidate: e.candidate.toJSON()}`。
- candidate 受信時に `pc.remoteDescription` が null なら配列にキュー。`addIceCandidate` の例外は握りつぶす（console.debug）。
- `blockIce = true` のとき：candidate を**送らず、受け取っても捨てる**（SDP には candidate が含まれないので接続は確立しない → タイムアウト経路のテスト用）。
- `isOpen` = 両チャネル `readyState === 'open'`。両方 open で `onOpen()`。
- どちらかの DC の `close`、または `pc.connectionState` が `failed`/`closed` で `onClose()`（一度だけ）。`disconnected` は無視（復帰し得る。生存監視で扱う）。
- `close()`：DC と pc を close。以降のイベントは無視。

### 2.7 `src/net/session.ts`

```ts
export type SessionPhase =
  | 'connecting'   // シグナリング WS 接続中
  | 'waiting'      // ホスト：相手待ち（code 確定）
  | 'joining'      // ゲスト：join_room 送信済み
  | 'negotiating'  // P2P 試行中、または中継の READY 待ち
  | 'ready'        // 経路確定（ホストは READY 受信済み）
  | 'closed';

export type CloseReason =
  | 'user'               // 自分で終了
  | 'bye'                // 相手が「タイトルへ」等で退出
  | 'peer_left'          // ゲスト視点：ホストが部屋を閉じた / ホスト視点（中継時）：ゲストの WS 切断
  | 'lost'               // 生存監視タイムアウト or Transport 切断
  | 'connect_timeout'    // 相手と経路を確立できなかった
  | 'server_unreachable' // シグナリングに接続できない / 応答なし
  | 'server_lost'        // シグナリング切断（経路確定前、または中継モード中）
  | SignalErrorCode;     // サーバーからの error

export interface SessionStatus {
  phase: SessionPhase;
  role: 'host' | 'guest';
  code: string | null;
  kind: TransportKind | null;  // negotiating 中は試行中の経路
  forcedRelay: boolean;        // ?forceRelay による中継か（トースト文言の切替に使う）
  rttMs: number | null;        // 直近 RTT の指数移動平均（α=0.2）
  unstable: boolean;           // 最後の受信から UNSTABLE_MS 超
  closeReason: CloseReason | null;
}

export class NetSession {
  static host(opts: NetOptions): NetSession;
  static join(code: string, opts: NetOptions): NetSession;
  readonly role: 'host' | 'guest';
  get status(): SessionStatus;
  onStatus: ((s: SessionStatus) => void) | null;   // phase/kind/unstable/closeReason が変わったときだけ
  /** ゲームメッセージ（ping/pong/ready は内部で処理し渡さない。bye は close('bye') に変換） */
  onMessage: ((m: GameMsg) => void) | null;
  send(m: GameMsg): void;  // encode + channelOf で Transport へ。ready 前は捨てる
  close(reason?: CloseReason): void; // 既定 'user'。ready なら BYE を reliable で送ってから閉じる
}
export interface NetOptions { signalUrl: string; iceServers: RTCIceServer[]; forceRelay: boolean; blockIce: boolean }
```

```ts
  /** カウントダウン開始（試合開始・再戦開始）。HUD を 0-0 にし playing 画面へ */
  matchStarted(): void;
  /** 相手が再戦を希望（結果画面に「相手は再戦を希望しています」） */
  peerWantsRematch(): void;
}
export interface MatchDriver {
  readonly kind: 'cpu' | 'host' | 'guest';
  readonly localSide: Side;
  /** 描画用の世界（ゲストは毎フレーム補間結果で上書き） */
  readonly world: World;
  readonly score: [number, number];
  /** 1 フレーム進め、このフレームで演出すべきイベントを返す */
  update(dt: number, localTarget: Vec2 | null): GameEvent[];
  requestRematch(): void;
  dispose(): void;
}
```

## 3. 接続シーケンスと状態遷移

### 3.1 定数（`src/net/config.ts`）

| 名前 | 値 | 用途 |
|---|---|---|
| `SIGNAL_CONNECT_TIMEOUT_MS` | 5000 | WS open 待ち |
| `SIGNAL_REPLY_TIMEOUT_MS` | 5000 | create_room / join_room の応答待ち |
| `P2P_TIMEOUT_MS` | 5000 | ホスト：peer_joined から READY（DC 経由）受信まで（SPEC の「5 秒」） |
| `RELAY_READY_TIMEOUT_MS` | 5000 | ホスト：中継切替から READY（中継経由）受信まで |
| `GUEST_CONNECT_TIMEOUT_MS` | 15000 | ゲスト：joined から MATCH_START 受信まで |
| `PING_INTERVAL_MS` | 1000 | ping 送信間隔 |
| `UNSTABLE_MS` | 1500 | 最後の受信からこれを超えたら「通信不安定」表示 |
| `LOST_MS` | 8000 | 最後の受信からこれを超えたら切断扱い |

シグナリング URL：`import.meta.env.VITE_SIGNAL_URL` があればそれ、無ければ
`${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws`（同一オリジン。推奨：開発も本番も同一オリジンにして証明書・CORS の問題を避ける）。

URL フラグ（`URLSearchParams`、値なしで有効）：`forceRelay`（中継を強制）、`blockIce`（ICE を遮断してタイムアウト経路を発生させる）、`e2e`（テスト用フック、§8）、`debug`（既存）。`room=XXXX`（招待）。

### 3.2 ホスト（P1）

```
[title] 「部屋を作る」
  └ NetSession.host()
     phase=connecting : SignalingClient.connect()（5s）
        失敗 → close('server_unreachable')
     send create_room{v}
        5s 応答なし → close('server_unreachable')
        error → close(code)
     room_created{code} → phase=waiting（待機画面にコード・QR・URL）
     ── peer_joined{forceRelay} ──▶ phase=negotiating
        useRelay = opts.forceRelay || msg.forceRelay
        useRelay なら → [中継へ切替] へ
        そうでなければ WebRtcTransport('host') を作り start()（offer 送信）
          P2P タイマー 5s 開始
          signal(answer/candidate) → transport.handleSignal()
          DC 経由で READY{v} 受信 → v 不一致なら close('version_mismatch')
                                   一致 → タイマー解除、phase=ready, kind='p2p'
          5s 経過（READY 未着）→ [中継へ切替]
     [中継へ切替]
          WebRtcTransport があれば close()（以降そこからの受信は無視）
          send signal{kind:'relay'}
          RelayTransport(sig) を作る。kind='relay'、RELAY タイマー 5s
          中継経由で READY 受信 → phase=ready, kind='relay'
          5s 経過 → 経路を破棄し phase=waiting に戻す（待機画面に「接続に失敗しました。もう一度参加してもらってください」）
     phase=negotiating 中に peer_left → 経路を破棄して phase=waiting（トースト「相手が退出しました」）
     phase=ready 以降は §6 の切断処理
```

- ready 後、`NetHostDriver` が生成され試合開始（§4.1）。
- ready 後も WS は**閉じない**（中継時は経路そのもの、P2P 時も peer_left の受信と M4 の再接続に使うため。サーバー負荷は ping 程度）。

### 3.3 ゲスト（P2）

```
[title] 「部屋に入る」→ [join] でコード入力（4 桁揃ったら自動送信） / URL ?room=XXXX なら入力を飛ばす
  └ NetSession.join(code)
     phase=connecting : connect()（5s）→ 失敗 close('server_unreachable')
     send join_room{v, code, forceRelay}
        5s 応答なし → close('server_unreachable') / error → close(code)
     joined → phase=negotiating, kind='p2p'（GUEST 15s タイマー開始）
        WebRtcTransport('guest') を作る（offer を待つ）
        signal(offer/candidate) → handleSignal()
        transport.onOpen → READY{v} を DC で送る
        signal{kind:'relay'} 受信（いつでも）→ WebRtcTransport を close、
             RelayTransport(sig) に切替、kind='relay'、READY{v} を中継で送る
        MATCH_START 受信 → phase=ready（タイマー解除）→ NetGuestDriver に渡す
        15s 経過 → close('connect_timeout')
        peer_left → close('peer_left')
```

- ゲストは自分では経路を決めない。**経路の決定権はホストのみ**（両者の判断が食い違う競合を無くすため）。DC が open していても `relay` を受けたら必ず従う。
- ゲストが READY を DC で送った直後にホストがタイムアウトで中継へ切り替えても、ゲストは `relay` を受けて中継で READY を再送するので整合する。
- `?room=` を読んだら `history.replaceState` で URL から `room` を消す（タイトルに戻ったとき・再読込で勝手に再参加しないため）。

### 3.4 状態遷移図（NetSession.phase）

```
             ┌──────────── error / timeout ─────────────┐
             │                                          ▼
 connecting ─┼─(host) room_created ─▶ waiting ─ peer_joined ─▶ negotiating ─ READY ─▶ ready ─▶ closed
             │                          ▲                          │  │
             │                          └─ peer_left / 中継READY ───┘  │（host: 5s で p2p→relay、kind だけ変わる）
             └─(guest) joined ─────────────────────────────▶ negotiating ─ MATCH_START ─▶ ready ─▶ closed
```
`closed` は終端。再挑戦は新しい NetSession を作る。

## 4. ゲームループ

### 4.1 ホスト（`NetHostDriver`）

```
constructor(session, hooks):
  host = new GameHost(); localSide = 1; world = host.world（reset のたびに参照し直す getter にする）
  lastSentTick = -1; lastSeq = -1; localRematch = peerRematch = false
  session.onMessage = onMessage
  startMatch()

startMatch():
  host.reset(); localRematch = peerRematch = false
  session.send({type:'match_start', startTick: host.tickCount})
  hooks.matchStarted()

onMessage(m):
  input  : if (!Number.isFinite(x,z) || |x|>2 || |z|>2) return            // SPEC 10: NaN・範囲外を拒否
           if (lastSeq >= 0 && !seqNewer(m.seq, lastSeq)) return          // 順不同到着の古いものは捨てる
           lastSeq = m.seq; const c = clampToHalf(2, m); host.setInput(2, c.x, c.z)
  rematch: peerRematch = true; localRematch ? startMatch() : hooks.peerWantsRematch()
  それ以外は無視

update(dt, target):
  if (target) host.setInput(1, target.x, target.z)
  evs = host.update(dt)
  for ev of evs: w = toWireEvent(ev); if (w) session.send({type:'event', tick: ev.tick, ev: w})
  if (host.tickCount !== lastSentTick) { session.send(stateMsg()); lastSentTick = host.tickCount }
  return evs

requestRematch(): localRematch = true; session.send({type:'rematch'}); if (peerRematch) startMatch()
```
- STATE は「1 フレームで 1 tick 以上進んだら最新状態を 1 回」送る。60Hz 表示なら 60Hz、120Hz 表示でも tick が進むのは 60Hz なので**最大 60Hz**。低 fps 時は 1 フレームで複数 tick 進むが最新のみ送る（古い中間状態は不要）。
- STATE は phase が `over` でも送り続ける（生存確認とゲストの描画継続のため。帯域は約 2.5KB/s で無視できる）。
- ホストはネット対戦中に一時停止しない（片方だけ止めると不公平なため）。ポーズボタンはメニューを開くだけで試合は進む。`visibilitychange` でもポーズしない。
- ゲスト入力が届かない間は、最後に適用した目標のまま（マレットはその場に留まる）。

### 4.2 ゲスト（`NetGuestDriver`）

```
constructor(session, hooks, matchStart):
  localSide = 2; world = createWorld(); interp = new Interpolator(delayFor(kind))
  local = world.mallets[1]（自マレットの実体）; seq = 0; sendAcc = 0; queue: EventMsg[] = []
  onMatchStart(matchStart.startTick)

onMatchStart(startTick):
  interp.reset(startTick); queue = []
  world = createWorld()（mallets[1] を初期位置に）; hooks.matchStarted()

onMessage(m):
  state       : interp.push(snapshotOf(m), performance.now()); score = m.score
  event       : queue.push(m)
  match_start : onMatchStart(m.startTick)
  rematch     : hooks.peerWantsRematch()

update(dt, target):
  now = performance.now()
  // 1) 自マレット：ホスト応答を待たずに即時移動（ホストと同じ速度上限で）
  if (target) moveMallet(local, clampToHalf(2, target), dt)
  // 2) 入力送信：最大 60Hz（アキュムレータ）。target が null（一度も触っていない）なら送らない
  sendAcc = min(sendAcc + dt, 0.1)
  if (target && sendAcc >= TICK_DT) { sendAcc %= TICK_DT; seq = (seq+1)&0xffff;
      session.send({type:'input', seq, x: target.x, z: target.z}) }
  // 3) 補間
  interp.delayTicks = session.status.kind === 'relay' ? 4 : 2
  if (interp.sample(now, s)) { world.puck ← s.puck（x,z,vx,vz）; world.puckActive = s.puckActive;
                               world.mallets[0] ← s.m1（x,z） }
  // 4) イベント：補間表示が追いついたものだけ発火
  out = []; while (queue[0] && (queue[0].tick <= s.renderTick || now - queue[0].recvAt > 250)) out.push(fromWireEvent(queue.shift().ev))
  return out

requestRematch(): session.send({type:'rematch'})
```
- 送信する入力は**クランプ前の生の target**（ホストが検証・クランプする。ゲストを信用しない）。描画はクランプ後。
- 自マレットの位置はホストから返る m2 で上書きしない（往復遅延分だけ引き戻されて見えるため）。両者とも同じ `clampToHalf` + `moveMallet` なので定常的なずれは生じない。
- イベントは受信時刻 `recvAt` を EventMsg に付けて保持する（ローカルフィールド）。tick 合わせにより、得点演出・火花が補間表示されたパックの位置と同時に出る。250ms の上限は STATE が途絶えて renderTick が進まない場合の保険。
- PuckTrail は `world.puck.vx/vz` から残光の強さを計算するので、補間結果に速度も入れること。

### 4.3 CPU（`LocalCpuDriver`）

- M1 の main.ts の処理をそのまま移す：`host.setInput(1, target)`、`cpu.update(host.world, dt)` → `host.setInput(2, ...)`、`host.update(dt)`。
- `requestRematch()` = `host.reset()` + `hooks.matchStarted()`。CPU の強さは main から `driver.cpu.level = s.cpu` で反映（`applySettings`）。
- **ネット対戦の経路では CpuPlayer を一切生成しない**（NetHostDriver / NetGuestDriver は CpuPlayer を import しない）。

### 4.4 main.ts の構成

```ts
type Mode = 'title' | 'hostWait' | 'join' | 'netMsg' | 'playing' | 'paused' | 'result';
let driver: MatchDriver | null = null;
let session: NetSession | null = null;
const idleWorld = createWorld();       // タイトル等で背景に描く
const ONLINE = import.meta.env.MODE !== 'artifact';   // ビルド時に定数化される
const RTC_OK = typeof RTCPeerConnection !== 'undefined';
```

- **`setLocalSide(side)`**：`view.localSide !== side` なら `scene.remove(view.root); view.dispose(); view = new TableView(side); scene.add(view.root)`。`rig.side = side; resize()`。`input.side = side`。CPU・ホストは 1、ゲストは 2。
- **CPU 練習**（`#start-btn`）：`setLocalSide(1)`、`driver = new LocalCpuDriver(settings.cpu, hooks)`。
- **部屋を作る**（`#create-btn`）：`sfx.unlock()`、`setLocalSide(1)`、`session = NetSession.host(opts)`、`show('hostWait')`。`session.onStatus` で待機画面を更新。phase=ready で `driver = new NetHostDriver(session, hooks)`、kind が relay ならトースト。closed で §6。
- **部屋に入る**（`#join-btn` / `?room=`）：`show('join')`、4 桁で `session = NetSession.join(code, opts)`。ゲストは phase=ready と同時に届いた MATCH_START を渡して `setLocalSide(2)`、`driver = new NetGuestDriver(session, hooks, matchStart)`。実装上は NetSession.join が `onMessage` で最初の `match_start` を受けたら phase=ready にしてから同じメッセージを onMessage に渡す。main は `driver` 未生成時に `match_start` を受けたら driver を作る。
- **hooks.matchStarted**：`input.target = null`、`updateScore([0,0], null)`、`resetResultButtons()`、`show('playing')`、`warmup = 2`、`requestWakeLock()`。
- **メインループ**：
  ```
  const runSim = driver && (driver.kind !== 'cpu' || mode === 'playing');
  if (runSim) for (const ev of driver.update(dt, mode === 'playing' ? input.target : null)) handle(ev);
  const w = driver?.world ?? idleWorld;
  view.sync(w); view.update(dt); trail.update(w); ...（以下 M1 と同じ）
  hud.setNet(session?.status ?? null)   // 値が変わったときだけ DOM 更新
  ```
- **handle(ev)**：M1 の `LOCAL` を `driver.localSide`、`CPU_SIDE` を `otherSide(localSide)` に置換。スコアは `ev.score[local-1]` / `ev.score[opp-1]`。
- **HUD ラベル**：`#who-opp` は CPU 時 `CPU`、ネット時 `RIVAL`。`#who-me` は常に `YOU`。aria-label は `相手の得点` / `あなたの得点`。
- **ポーズ**：CPU 時は M1 と同じ。ネット時はポーズ画面の `再開` は単に閉じる、`最初からやり直す` は非表示、`タイトルへ` は `session.close('user')`（BYE 送信）→ `show('title')`。`visibilitychange` によるポーズは CPU 時のみ。
- **結果画面**：`もう一度` → `driver.requestRematch()`。ネット時はボタンを disabled にし文言を `相手を待っています…` に。`hooks.peerWantsRematch` で `#result-note` に `相手は再戦を希望しています`。`タイトルへ` は ネット時 `session.close('user')`。
- **タイトルへ戻るとき**は必ず `driver?.dispose(); driver = null; session?.close(); session = null; setLocalSide(1)`（描画は idleWorld）。
- **Artifact 分岐**：`if (!ONLINE || !RTC_OK)` なら `#create-btn` `#join-btn` を `hidden`、`#start-btn` を primary にし、note を §3.5 の文言に。`ONLINE` が false のとき `?room=` は無視。ネット関連モジュール（`./net/session`, `./match/net-host`, `./match/net-guest`, `./ui/qr`）は **`if (ONLINE)` の内側で動的 import** する。これにより artifact ビルドではデッドコードとして消え、WebRTC/qrcode が混入しない（受け入れ基準で grep 確認）。
- 既存の性能監視・フラッシュ・トーストはそのまま（`ui/hud.ts` に移すだけ）。

## 5. 補間アルゴリズム（`src/sync.ts`）

定数：

| 名前 | 値 | 理由 |
|---|---|---|
| `DELAY_TICKS_P2P` | 2（33ms） | SPEC 7.4 の 16〜33ms の上限。LAN のジッタ 1 tick を吸収 |
| `DELAY_TICKS_RELAY` | 4（67ms） | TCP 中継はジッタが大きい |
| `MAX_EXTRAP_TICKS` | 6（100ms） | これ以上はパックの外挿誤差（最大 50cm）が目立つ |
| `SNAP_TICKS` | 8 | 目標とのずれがこれを超えたら即座に合わせる |
| `TIME_WARP` | 0.08 | 再生速度の補正幅 ±8%（体感できない範囲） |
| `BUFFER_MAX` | 32 | 約 0.5 秒分 |

```
push(s, now):
  if (s.tick < minTick) return                       // 前の試合の遅延パケット
  if (newest && s.tick <= newest.tick) return         // 重複・順不同（unordered チャネル）
  buf.push(s); if (buf.length > BUFFER_MAX) buf.shift()
  lastArrivalMs = now
  if (renderTick === null) { renderTick = s.tick - delayTicks; lastSampleMs = now }

sample(now, out):
  if (!newest) return false
  dtTicks = (now - lastSampleMs) * 60 / 1000; lastSampleMs = now
  // 最新 tick の「今の推定値」（パケットが来なくても時間で進むが、外挿上限まで）
  newestEst = newest.tick + min((now - lastArrivalMs) * 60 / 1000, MAX_EXTRAP_TICKS)
  target = newestEst - delayTicks
  renderTick += dtTicks
  err = target - renderTick
  if (|err| > SNAP_TICKS) renderTick = target
  else renderTick += clamp(err, -TIME_WARP * dtTicks, +TIME_WARP * dtTicks)
  renderTick = min(renderTick, newest.tick + MAX_EXTRAP_TICKS)
  // 古いスナップショットの掃除：renderTick 以下のものは直前の 1 つだけ残す

  if (renderTick <= buf[0].tick)        → out ← buf[0]（そのまま）
  else if (renderTick >= newest.tick)    → 外挿
      e = min(renderTick - newest.tick, MAX_EXTRAP_TICKS) / 60   // 秒
      puck = newest.puckActive ? newest.puck + v*e : newest.puck  // 速度はそのまま
      puck.x を ±(HALF_W - PUCK_R) にクランプ
      |puck.x| > GOAL_W/2 - PUCK_R なら puck.z を ±(HALF_L - PUCK_R) にクランプ（ゴール口以外は壁を越えない）
      m1 = newest.m1（相手マレットは外挿しない：動きが不規則なため停止させる方が自然）
  else                                    → 補間
      a = renderTick 以下で最大 tick、b = その次
      α = (renderTick - a.tick) / (b.tick - a.tick)
      teleport = a.puckActive !== b.puckActive
              || dist(a.puck, b.puck) > (b.tick - a.tick) * PUCK_MAX_SPEED / 60 + 0.05
      puck = teleport ? a.puck : lerp(a.puck, b.puck, α)（x,z,vx,vz すべて）
      puckActive = teleport ? a.puckActive : b.puckActive && a.puckActive
      m1 = lerp(a.m1, b.m1, α)
  out.renderTick = renderTick
```

- tick 基準なので、ホストのフレームレートや送信タイミングの揺れに影響されない（STATE の間隔が 2 tick 空いても α で正しく補間される）。
- サーブ・リスタート（`placePuck`）やゴール後の消失は teleport として扱い、盤上を横切る補間をしない。
- パケットロス：最大 100ms までは外挿、その後は外挿位置で停止。STATE が `UNSTABLE_MS` 以上途絶えたら `#net-status` を「通信不安定」に（§6）。復帰時はずれが `SNAP_TICKS` を超えていれば一気に合わせ、以内なら ±8% で追いつく。
- 線形補間で壁反射の角がわずかに丸まるが、1 tick（最大 8cm）以内の現象で、残光トレイルに紛れるため許容する（Hermite 補間は M5 の予測と合わせて検討）。

## 6. 切断検知と扱い

**判断：M2 では再接続は作らず、切断＝その試合の終了とする。再接続（SPEC 7.5 の 30 秒待ち・復帰）は M4。**
理由：再接続はホスト側の試合状態保持・ルーム再入室・WebRTC 張り直し・UI の一時停止状態が絡み、M2 の「接続して対戦・得点できる」の完了条件には不要なため。ただし M4 で足しやすいよう、WS はマッチ中も維持し、切断理由を `CloseReason` で区別しておく。

検知（NetSession 内、`setInterval(250ms)` で監視）：

| 事象 | 判定 | 結果 |
|---|---|---|
| 相手の BYE 受信 | 即時 | `close('bye')` |
| Transport の onClose（DC close / pc failed / 中継時の WS close） | 即時 | `close('lost')`（中継時の WS close は `server_lost`） |
| 最後のゲームパケット受信から `UNSTABLE_MS`(1.5s) | 監視 | `status.unstable = true`（表示のみ。受信で解除） |
| 最後のゲームパケット受信から `LOST_MS`(8s) | 監視 | `close('lost')` |
| `peer_left`（ready 後） | 即時 | 中継時：`close('lost')`。P2P 時：**無視**（DC が生きていれば試合継続。生存監視に任せる） |
| シグナリング WS 切断（ready 後・P2P 時） | 即時 | 無視（試合は DC で継続） |

- 生存監視の「受信」は全ゲームパケット（ホストは 60Hz の INPUT が来ないこともあるので、PING を双方 1 秒ごとに送り、受けた側は PONG を返す）。RTT = `now - pong.t`、EMA(α=0.2)。
- ping/生存監視は phase=ready になってから開始。
- 切断後の画面：両者とも試合を止め（driver.dispose）、通信メッセージ画面（§3.5）。勝敗はつけない。
- ホストのタブが裏に回ると rAF が止まり STATE が途絶える。ゲストは 1.5 秒で「通信不安定」、8 秒で終了（M2 の仕様として許容。M4 で一時停止イベント `pause` を追加する）。

### 7.3 サーバー（`server/main.ts` / `server/signaling.ts` / `server/rooms.ts`）

- 環境変数：`PORT`（既定 8787）、`HOST`（既定 `0.0.0.0`）、`STATIC_DIR`（既定 `dist`。存在しなければ静的配信なし＝開発時）。
- HTTP：`GET /healthz` → `200 ok`。それ以外の GET は `STATIC_DIR` から配信（`path.resolve` 後に STATIC_DIR 配下かを確認しディレクトリトラバーサル防止。存在しないパスは `index.html`。`/assets/*` は `cache-control: public, max-age=31536000, immutable`、それ以外 `no-cache`。MIME：html, js, css, svg, png, ico, json, webmanifest, woff2）。
- WS：`new WebSocketServer({ server, path: '/ws', maxPayload: 64 * 1024 })`。
  - テキスト：`parseClientMsg` → null なら `error{bad_request}`。
  - バイナリ：512 byte 超は破棄。同じ部屋の相手がいれば**そのまま転送**（中継）。
  - ハートビート：15 秒ごとに `ws.ping()`、前回の pong が無ければ `terminate()`。
  - close → `rooms.leave(peer)`。
- `RoomManager`（純粋ロジック）：
  ```ts
  export interface Peer { readonly id: number; send(m: ServerMsg): void; sendBinary(d: Uint8Array): void }
  export interface RoomOptions { maxRooms?: number /* 5000 */; randomInt?: (n: number) => number /* crypto.randomInt */ }
  export class RoomManager {
    constructor(opts?: RoomOptions);
    create(p: Peer, v: number): void;
    join(p: Peer, code: string, v: number, forceRelay: boolean): void;
    signal(p: Peer, data: SignalData): void;   // 相手がいれば signal として転送、いなければ捨てる
    relay(p: Peer, data: Uint8Array): void;
    leave(p: Peer): void;
    get size(): number;
    roomOf(p: Peer): string | null;            // テスト用
  }
  ```
  規則：
  - 1 ソケットは最大 1 部屋。既に所属していて create/join → `already_in_room`。
  - `v !== PROTO_VERSION` → `version_mismatch`（join 時はホストの v とも比較）。
  - コード：`String(randomInt(10000)).padStart(4, '0')`、使用中なら最大 50 回再抽選、だめなら 0000 から空きを線形探索。部屋数 ≥ maxRooms → `server_full`。
  - join：コード形式不正 → `bad_request`、無い → `room_not_found`、ゲストあり → `room_full`。成功で ゲストに `joined{code}`、ホストに `peer_joined{forceRelay}`。
  - leave（ホスト）：部屋を削除し、ゲストがいれば `peer_left`。leave（ゲスト）：ゲスト枠を空け、ホストに `peer_left`（部屋は残り、別の人が参加できる）。
  - Origin 制限・レート制限は M5（M2 では maxPayload とバイナリ上限のみ）。

  1. P1 `/?e2e` → `#create-btn` クリック → `#room-code` が `/^\d{4}$/` になるまで待つ。
  2. P2 `/?e2e&room={code}`。
  3. 両者 `net.phase==='ready' && net.kind==='p2p'`、`mode==='playing'`（10 秒以内）。P2 は `localSide===2`、P1 は `localSide===1`。
  4. STATE が流れる：P2 の `lastStateTick` が 1 秒で 30 以上増える（headless のソフトウェア描画で fps が落ちても通る閾値）。
  5. 入力と P2 視点：P2 で `page.mouse.move` を canvas の下部 1/4・右寄り（x=0.8w, y=0.8h）へ。→ 100ms 以内に P2 自身の `mallets[1]` が目標付近へ動く（ホスト応答を待たない即時描画）、500ms 以内に P1 の `mallets[1]` が `x < 0 && z < 0`（P2 カメラは反転しているので画面右＝ワールド −x）。左寄り（0.2w）に動かすと P1 側で `x > 0`。
  6. P1 も同様に mouse.move（x=0.8w）→ P1 の `mallets[0].x > 0`、P2 の `mallets[0].x > 0`（補間経由）。
  7. 得点：`phase==='playing'` を待ち `forceGoal(1)` → P1 `#score-me`=1、P2 `#score-opp`=1（3 秒以内）。`phase==='playing'` を待ち `forceGoal(2)` → P2 `#score-me`=1、P1 `#score-opp`=1。
  8. 試合終了：`forceGoal(1)` を計 7 点まで繰り返す → 両者 `#result` 表示、P1 `#result-title`=`YOU WIN`、P2=`YOU LOSE`、P2 `#result-score`=`1 – 7`。
  9. 再戦：P2 `#again-btn` → P1 に `#result-note` 表示 → P1 `#again-btn` → 両者 `mode==='playing'`、スコア 0-0。
  10. 退出：P2 で `#pause-btn` → `#quit-btn` → P1 に `#net-msg` 表示、本文に `相手が退出しました`。
  11. 失敗時・終了時に `e2e/out/{scenario}-p1.png` / `-p2.png` のスクリーンショット保存（P2 画面でシアンのマレットが手前に見えることを人が確認できるように）。
- **B. 中継強制**：P2 を `/?e2e&forceRelay&room={code}` → 両者 `kind==='relay'`（3 秒以内。P2P 試行をしないので即時）、A-4・A-7 と同じ確認。
- **C. 自動フォールバック**：P1 を `/?e2e&blockIce` → P2 参加後、両者 `kind==='relay'` かつ `mode==='playing'` が 9 秒以内（P2P 5 秒 + 余裕）、5 秒より前には relay にならない。トースト `直接つながらなかったため` が表示される。A-7 の得点確認 1 回。
- **D. エラー**：
  - 存在しないコード（作成済みコードと異なる 4 桁）で参加 → `#net-msg-text` に `見つかりません`。
  - 対戦中の部屋に 3 つ目のコンテキストで参加 → `すでに対戦中`。
  - ホスト側ページを `page.close()` → ゲストに `#net-msg`（`接続が切れました` か `部屋を閉じました` のどちらか、10 秒以内）。
- 結果を `PASS A` 等で出力し、1 つでも失敗なら exit code 1。終了時にサーバープロセスを kill。全体のタイムアウト 180 秒。

### 8.4 中継フォールバックを強制する方法（まとめ）

| 方法 | 効果 | 用途 |
|---|---|---|
| `?forceRelay`（P1/P2 どちらでも） | ホストが P2P を試さず即 `relay` を指示 | 中継経路そのものの確認、公衆 Wi-Fi で P2P が無理と分かっている時の手動回避 |
| `?blockIce`（P1 に付ける） | ICE 候補を送受信しない → P2P が確立せず 5 秒タイムアウト → 自動フォールバック | フォールバック経路（タイマー・切替・ゲストの追従）の確認 |

## 9. M2 でやらないこと（スコープ外）

- 切断後の再接続・30 秒待機・一時停止イベント（SPEC 7.5）→ M4。
- 試合中のポーズの同期（ネット対戦ではポーズしない）→ M4。
- パックのローカル予測・誤差補正、補間遅延の動的調整、Hermite 補間 → M5。
- 試合中の経路切替（P2P が途中で切れたら中継に移る等）→ 切断扱い。必要なら M5。
- TURN サーバー。
- アプリ内 QR 読み取り、独自テンキー UI、タイトル以外の画面デザインの作り込み → M4。
- 本番デプロイ設定（Dockerfile / fly.toml）、Origin 制限・レート制限、PWA → M5。
- ルームの有効期限・観戦・3 人目以降の待機列・ホスト移譲。
- ネット対戦での設定同期（視点・エフェクトは各端末ローカルのまま）。
- CPU 対戦の改良（M6）。
